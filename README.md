## TIMESTAMPS
The goal of the timestamp usage in the protocol is to prevent from replay attacks. Meaning adversary should not be able to copy ciphertext and try to resend it, so parties will think they participate in real protocol. Timestamps are used in a way that adversary can actually perform replay attack, but only within 5 seconds window, as a documenation states. 

Metodology: <br>
There is a need for two families of models
    1. Models with timestamp omited, so I capture what properties models have when adversary succesfully perform replay attack.
    2. Models with ideal timestamp - Parties do not accept wrong messages with wrong timestamp. Tamarin can't model time flow in form that is required for realistic timestamps. Meaning it can't check whether particular time (example 5 seconds) have passed or not. Tamarin can only express order of events but this can't be used to capture timestamp. 

    Nevertheless we can capture timestamp by simply requiring them to be unique. Meaning parties do not accept messages with two the same timestamps. It means that honest parties and adversary can produce correct timestamps, but no honest party accepts messages with two the same (wrong) timestamps. 

    Note that this is exaclty what timestamps are designed for, but in an ideal form.

### properties List
#### `lemma key_secrecy`
The session key `k` computed by the Device in `Device_send_params` is never learned by the adversary (`K(k)` never occurs).

### DL view: bindings between `k`, `D_ID` and `otID`

#### `lemma DL_k_bind_D_ID`
Key → Device ID. A session key `k` finalised by the DL is never associated with two different Device IDs. One key identifies at most one `D_ID`.

#### `lemma DL_D_ID_bin_k`
Device ID → key. A Device ID generated by the DL is never associated with two different session keys. One `D_ID` identifies at most one key.

#### `lemma DL_k_bind_otID`
Key → one-time ID. A session key `k` finalised by the DL is never associated with two different one-time IDs. One key comes from at most one registration session.

#### `lemma DL_otID_bind_k`
One-time ID → key. A one-time ID `otID` never leads to two different session keys at the DL. One registration session yields at most one key.

#### `lemma No_forks`
A registration session does not "fork". For a given pair `(k1, otID1)` finalised by the DL, either no other key is ever derived for `otID1`, or `k1` is never derived for another `otID`. It is expected to follow from the four binding lemmas above.

### Key correctness

#### `lemma all_keys_in_DL_come_from_devices_params`
Every key finalised by the DL is derived from the parameters of some real Device (`D_params`), using the key-derivation function of the model. The DL never ends up with a key built from adversary-supplied or garbage parameters.

#### `lemma all_Device_keys_come_from_devices_params`
The same property for the Device: every key with which the Device finishes registration is derived from genuine Device parameters.

### Binding between Device and DL

#### `lemma D_ID_binds_keys`
Agreement on the key. If the DL and the Device finish with the same `D_ID`, they hold the same session key.

#### `lemma key_bind_D_IDs`
Agreement on the identity. If the DL and the Device finish with the same session key, they also hold the same `D_ID`.

### the most important lemma: 
#### `lemma all_DL_keys_match_Device_keys`
Every key with which a Device finishes registration was previously finalised by the DL. The Device never accepts a key that the DL does not hold.

#### `lemma freshness`
No replay of ciphertexts. If the Device finishes with a ciphertext `c`, it never finishes with that same `c` again. Every accepted ciphertext is used exactly once.

## Sending message lemmas

### Secrecy

#### `lemma DV_message_secrecy`
Every message `m` sent by a Device (`Dv_sent_m`) is never learned by the adversary (`K(m)` never occurs).

#### `lemma DL_message_secrecy`
Every message `m` sent by the DL (`DL_sent_m`) is never learned by the adversary (`K(m)` never occurs).

### Authentication

Messages `m` are fresh and, because secrecy holds, unknown to the adversary. Therefore the only possible source of `m` is the believed sender.

#### `lemma DL_rcv_auth`
If the DL receives a message `m` and believes it comes from the Device with identity `D_ID`, then this Device really sent that exact message with that identity earlier (`Dv_sent_m(m)` and `DV_sent_ID(D_ID)` at some `#j < #i`).

#### `lemma Dv_rcv_auth`
If a Device receives a message `m` and believes it comes from the DL, then the DL really sent that exact message earlier (`DL_sent_m(m)` at some `#j < #i`).

#### `lemma freshness_DL`
Protection against replay on the DL side. The DL never receives the same ciphertext `c` twice. If the DL receives a given `c` at two points in time, those two points are in fact the same event, so a ciphertext recorded by the attacker cannot be replayed to the DL.

#### `lemma freshness_Dv`
Protection against replay on the Device side. The Device never receives the same ciphertext `c` twice. If the Device receives a given `c` at two points in time, those two points are in fact the same event, so a ciphertext recorded by the attacker cannot be replayed to the Device.

### Integrity
No separate lemma is needed. If authentication holds, integrity holds as well: the adversary cannot provide any ciphertext that the receiver accepts, unless the message is exactly the one constructed by the sender.

## Device_to_Device
I found something. Generally, the protocol does not describe how to use the `ad` (associated data) of AEAD. I used IDs as `ad`, because they were sent in plaintext. In step 2, the DL sends `kad` to the Initiator. Firstly, I used the Initiator's ID as `ad`, as it was sent in plaintext, but then it does not provide authentication. Meaning, if the Initiator runs two protocol instances at the same time, he can't distinguish the DL's responses, so he can mix them up. Therefore, I use the Recipient's ID (`IDb`) as `ad` in DL step of LAAFFI.
